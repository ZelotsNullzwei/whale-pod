## 一、现象（有日志可查，可复现）

DeepSeek 的**输入端内容审核**在私聊成人场景下反复拒答。

```
2026-11-07T16:39:21  decision/model
2026-11-07T16:39:22  decision/model   ×2
2026-11-07T16:39:33  decision/model
2026-11-07T16:39:34  decision/model   ×2
2026-11-07T17:05:59 … 17:08:31        decision/model   ×15
```

- 全日志共 **21 条**，**100% 来自 `decision/model`**（判断"该不该接话"的那次调用）
- **生图层 0 条** —— 同一批消息在 16:39:27 正常出了回复
- 拒答原文固定：

```
抱歉，系统检测到您当前输入的信息存在敏感内容，我无法响应您的请求，请检查后重新输入。
```

- 日志形态：

```
[warn] decision/model：解析不出 verdict（原始="抱歉，系统检测到您当前输入的信息存在敏感内容…"），重试 2/1
[info] decision/model：私聊解析失败（原始="…"）
```

**注意一个读数陷阱**：`retryOnBad = 1` 表示首次 + 重试 1 次 = 每轮 **2 次调用**，各打一条 warn，再加一条 info。所以"2 轮拒答"在日志里显示成 6 行。看行数会以为发生 6 次。

**根因**：决策请求把**最近 15 条原始聊天**整段塞进模型，私聊场景下那段就是最露骨的原文 → 撞输入端审核。不是我们的提示词写错了，是**上游拒绝看这段内容**。

## 三、当前影响（为什么还不算致命）

- 只损失"该不该接"的判断精度，**不丢消息**：私聊 fallback 成"必回"，群里退回规则引擎
- 代价：
  - 每轮多一次无效调用（实测 2–7 秒）
  - 日志噪音，容易误判成"她不回话了"
  - 决策精度下降（本该沉默的时候可能被规则判成接）

## 四、候选方案（要评审）

### A. 决策输入脱敏
送进决策层之前，把露骨词替换成中性占位（`…动作…` / `…身体接触…`），保留语义骨架和轮次结构。

- 优点：一处改动，群/私聊都受益；不依赖渠道
- 风险：**脱敏可能把判断依据也削掉**（"他这句到底是不是在撩"依赖原文温度）；替换表要维护

### B. 私聊跳过决策层
私聊规则本来就是"必回"（`decision/model.js:505` 的注释自己写了"退回 rule 毫无意义"）。

- 优点：直接省掉一次调用和全部拒答；逻辑上本来就冗余
- 风险：会不会丢掉只有模型能判的语义？比如 close.md 里「他说要收/要走，多半是台阶；想继续就拉，真不想就干脆放行」—— 这类判断现在可能依赖模型

### C. 认出拒答就不再重试
匹配拒答前缀，**立即**退回规则，不再浪费第二次调用。

- 优点：改动最小、零风险
- 缺点：只止损，不解决精度

### D. 决策层换渠道
换一个不审输入的小模型，或纯本地规则。

- 优点：彻底绕开
- 风险：多一个依赖；本地规则判断力弱

## 五、要 Grok 判断的具体问题

1. **A 的脱敏边界怎么定**？换词、删句、还是压成"说话人+意图"摘要？哪种最不伤判断力？
2. **B 会不会破坏现有语义**？私聊跳过决策层之后，close.md 里那些"读空气"的规则还有没有生效路径？
3. **群聊要不要同一套**？现在群里 0 次拒答，但话题放开后大概率会遇到。
4. 有没有**第五种**做法我没列？比如把决策输入改成我们自己生成的中性滚动摘要，而不是原文？
5. **风控累积**：同一个 key 反复触发输入端审核，会不会有账号级风险？这点我无法从代码验证。

## 六、明确不要做的

- ❌ 不要去改 persona 里"允许露骨"的写法来提高通过率 —— 拦住的是**输入端内容**，改提示词无效

- ❌ 不要为了少几条 warn 就把 `retryOnBad` 设 0 —— 那会把真正的格式错误也一起牺牲
